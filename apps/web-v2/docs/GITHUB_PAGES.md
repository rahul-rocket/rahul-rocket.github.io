# GITHUB PAGES

Everything specific to hosting a Next.js static export on GitHub Pages. The
constraints here shaped the architecture more than any other single factor
([ARCHITECTURE.md](./ARCHITECTURE.md) §7), so this document is required reading
before implementing any route.

## 1. The hosting model

GitHub Pages is a **static file server with a CDN**. It serves files. It runs no
code, sets no custom headers, performs no redirects, and has no configuration
beyond a branch/directory choice.

Consequences: no API routes, no middleware, no server actions, no ISR, no
on-demand image optimization, no custom security headers, no server-side
redirects. Each has a documented workaround in §5–§6.

## 2. User site, not project site — and why it matters

This repository is named `rahul-rocket.github.io`, which makes it a **user
site**. That is a meaningful advantage:

| | User site (`user.github.io`) | Project site (`user.github.io/repo`) |
| --- | --- | --- |
| Served at | `https://rahul-rocket.github.io/` | `https://rahul-rocket.github.io/repo/` |
| `basePath` | **Not needed** (`''`) | Required, and it leaks into every asset path |
| `assetPrefix` | Not needed | Required |
| Root-relative links | Work naturally | Break unless every one is prefixed |

Because this is a user site, `basePath` stays `''`. **`siteConfig.basePath`
exists anyway** ([PROJECT_STRUCTURE.md](./PROJECT_STRUCTURE.md) §4) so that the
value is threaded through helpers from day one — if the site is ever moved to a
project repo, it becomes a one-line change rather than an audit of every `href`.

## 3. Required configuration

### `next.config.mjs`

```js
export default {
  output: 'export',            // static HTML export to out/
  trailingSlash: true,         // /blog/post/ → /blog/post/index.html
  images: { unoptimized: true },
  basePath: '',                // user site
  reactStrictMode: true,
};
```

**`trailingSlash: true` is mandatory, not stylistic.** Without it, Next emits
`out/blog/post.html`, and GitHub Pages will not serve that at `/blog/post`.
With it, Next emits `out/blog/post/index.html`, which Pages serves at
`/blog/post/` natively. Every canonical URL, sitemap entry, and internal link
must use the trailing-slash form consistently, or canonicals disagree with the
served URLs ([SEO.md](./SEO.md) §7).

### `public/.nojekyll`

**Required, and its absence is a silent failure.** GitHub Pages runs Jekyll by
default, and Jekyll ignores any file or directory beginning with an underscore —
which is exactly where Next places `_next/static/*`. Without `.nojekyll` the
site deploys successfully and then loads with no CSS and no JS. The file is
empty; its existence is the signal. A CI assertion checks that it survives into
`out/`.

## 4. Routing behavior

| Request | Served |
| --- | --- |
| `/` | `out/index.html` |
| `/about/` | `out/about/index.html` |
| `/about` | 301 → `/about/` (Pages adds the slash) |
| `/blog/post/` | `out/blog/post/index.html` |
| `/nonexistent` | `out/404.html` with a 404 status |
| `/_next/static/…` | Hashed asset, cached immutably |

**Every dynamic route must be enumerable at build time** via
`generateStaticParams`, driven by the content file list. There is no fallback
rendering — a URL that was not generated is a 404.

**The 404 page is real.** `app/not-found.tsx` exports to `out/404.html`, which
GitHub Pages serves automatically for unknown paths, with a correct 404 status
code. No SPA-redirect hack is needed, and the well-known
`404.html → index.html?redirect=` trick is explicitly **not** used: it breaks the
status code, confuses crawlers, and flashes the wrong content.

## 5. Constraint workarounds

| Missing | Workaround |
| --- | --- |
| API routes | Contact form POSTs to Formspree; `mailto:` fallback ([WEBSITE_STRUCTURE.md](./WEBSITE_STRUCTURE.md) §4.12) |
| Server-side redirects | Generated static stub pages (§6) |
| Custom headers (CSP, HSTS) | `<meta http-equiv="Content-Security-Policy">` where honored; the rest is unavailable — see §8 |
| ISR / revalidation | Rebuild on push + a nightly cron ([DEPLOYMENT.md](./DEPLOYMENT.md) §6) |
| Image optimization API | Build-time responsive AVIF/WebP generation |
| Live third-party data | Fetched at build by the workflow, committed or emitted as JSON |
| Server-side form validation | Client validation + the endpoint's own validation; honeypot anti-spam |

## 6. Redirects

There is no redirect mechanism, so a moved URL is handled by generating a stub
page at the old path:

```html
<!-- out/blog/old-slug/index.html -->
<meta http-equiv="refresh" content="0; url=/blog/new-slug/">
<link rel="canonical" href="https://rahul-rocket.github.io/blog/new-slug/">
<p>This page has moved to <a href="/blog/new-slug/">…</a>.</p>
```

Stubs are declared in a single `config/redirects.ts` map and generated by the
build, so they are reviewable in one place. The canonical tag is what preserves
search equity; the visible link is what preserves the no-JS reader. This is a
weaker instrument than a 301 — it is the honest cost of static hosting, and it is
the reason slugs are treated as permanent ([CONTENT_STRATEGY.md](./CONTENT_STRATEGY.md) §7).

## 7. Custom domain migration (designed for, not done)

1. Add `public/CNAME` containing the bare domain.
2. Configure DNS: `ALIAS`/`ANAME` at the apex to `rahul-rocket.github.io`, or
   four `A` records to GitHub's Pages IPs; `CNAME` for `www`.
3. Enable **Enforce HTTPS** in repository settings once the certificate issues
   (can take up to 24 hours).
4. Change `siteConfig.url`. Every canonical, OG URL, sitemap entry, and feed link
   follows automatically because all of them derive from that one value
   ([SEO.md](./SEO.md) §12).
5. Submit a change of address in Search Console. The `github.io` host continues
   to serve, so old links keep working.

Total application change: one string.

## 8. Security headers — the honest limitation

GitHub Pages sets no custom headers. `Content-Security-Policy`,
`Strict-Transport-Security`, `X-Frame-Options`, and `Permissions-Policy` cannot
be delivered as headers.

Partial mitigations: a `<meta http-equiv="Content-Security-Policy">` tag (honored
for most directives, but `frame-ancestors` and `report-uri` are header-only), and
`referrerpolicy` / `rel="noopener noreferrer"` on outbound links.

Residual risk is **low for this site**: no authentication, no cookies, no user
data, no user-generated content, and no third-party scripts. The exposure that
headers would mitigate largely does not exist here. This is stated plainly rather
than glossed, and it is the one concrete reason a future move to Cloudflare Pages
or Netlify would be worth considering.

## 9. Caching

| Path | Behavior |
| --- | --- |
| `/_next/static/*` | Content-hashed; effectively immutable |
| HTML | Short cache; Pages purges its CDN on deploy |
| `/public/*` non-hashed | Short cache — version filenames when it matters (e.g. the résumé PDF) |

Cache headers are not controllable, so cache-busting is done through filenames.
The résumé PDF is therefore versioned `rahul-rocket-resume-YYYY-MM.pdf`.

## 10. Limits

| Limit | Value | Headroom |
| --- | --- | --- |
| Repository size | 1 GB soft | Vast — export target is ≤ 15 MB |
| Published site size | 1 GB | Vast |
| Builds per hour | 10 soft | Fine; deploys are per-push |
| Bandwidth | 100 GB/month soft | Far beyond realistic traffic |

The real constraint is Git history growth from committed images, which is why
source images are capped at 500 KB by a pre-commit hook
([CONTENT_STRATEGY.md](./CONTENT_STRATEGY.md) §10).

## 11. Local verification

The dev server hides the three things that actually break on Pages:
`trailingSlash` behavior, the real 404, and production asset paths.

```bash
pnpm build && pnpm start   # serves out/ statically — the only faithful preview
```

Before any release: verify a deep link with and without a trailing slash, a hard
refresh on a nested route, the 404 page at a bogus URL, an `og:image` URL opened
directly, and the site with JavaScript disabled.

## 12. Migration from the legacy deployment

The repository currently deploys a Create React App build from `./build` to a
`gh-pages` branch via `peaceiris/actions-gh-pages@v3`.

The replacement uses the official Pages actions (`actions/configure-pages`,
`upload-pages-artifact`, `deploy-pages`) publishing `out/` — no `gh-pages`
branch, OIDC-based permissions rather than a token, and a native deployment
environment with rollback. The cutover sequence is in
[DEPLOYMENT.md](./DEPLOYMENT.md) §7; the legacy workflow keeps running until the
new site is ready, so the live site is never broken by this repository's
in-progress state.
